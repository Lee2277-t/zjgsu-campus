> 27–35 这些是本轮及前几轮新增的。它们的共同点是：**没建也不会崩，但对应功能会静默失效**
> —— 通知中心不写通知、审核不留痕、图片审核没记录、注销申请存不下、错误一条都收不到、
> 留言点赞走降级路径（按钮照样有反应，但计数可能重复）、留言一条都发不出去（评论区和
> 详情页都依赖 `post_comments`）、申诉提交不上。
> 正因如此才更要建：它们的失败都不产生前台报错。
>
> `content_protects` 没建的表现最隐蔽：保护按钮点了没反应（写不进去），
> 而运营会以为护住了 —— 直到那条内容被几个人举报到自动下架才发现。
>
> `post_drafts` 没建的表现是「换设备后草稿箱是空的」：本机照常能存能恢复，
> 所以几乎没人会怀疑是集合没建 —— 直到他换了手机。
>
> `content_views` 没建的表现最像「规则改了但没用」：举报下架门槛按**独立浏览人数**分档
> （0-49 → 3 人 / 50-199 → 5 人 / 200-499 → 7 人 / 500+ → 10 人），
> 集合没建时分母恒为 0，所有内容都落回最低档 3 人 ——
> **一条几千人看过的热议帖，仍然是三个人举报就被收起来**，而页面不会有任何报错。
> 「我的 → 环境自检」会把这一条列出来。

> `comment_votes` 为什么必须独立成表，不能塞进 `posts` 文档的 comments 数组里：
> 留言数组是**整份下发到客户端**的，把「谁赞了哪条」也塞进去，等于把全校的投票名单
> 发给每个人（openid 虽不能直接认人，但配上留言内容足够推断出很多东西）；
> 而且帖子文档有 **1MB 上限**，留言本来就能到 200 条，先撞线的就是它。

### 1.1 `post_comments` 为什么从 `posts` 里拆出来

留言原来存在帖子的 `comments` 数组里。三个 action（发留言 / 删留言 / 回写赞踩计数）
都是「读整份数组 → 改 → 整份写回」，并发时后写的会把先写的整份覆盖：
两个人同时留言会丢一条；别人刚发的留言，被另一个人点赞时整份盖回旧值就没了。
这类丢失**没有任何报错**，只表现为「我明明发了，刷新就没了」。

拆开之后：

| 操作 | 以前 | 现在 |
|---|---|---|
| 新增留言 | 读 200 条 → 追加 → 整份写回 | `doc(id).set()` 只写自己这一条 |
| 删除留言 | 过滤数组 → 整份写回 | 软删（`removed: true`），批量按 id 更新 |
| 点赞 | 读出下标 → 改计数 → 整份写回 | `doc(id).update({ likes, dislikes })` |
| 列表条数 | `comments.length` | `posts.commentCount`（原子 `inc`） |

字段（除 `id` 外都可缺省，老留言零迁移）：

```js
{
  _id: 'c1759...',        // = 留言 id，点赞/软删都靠它定位
  postId: 'p...',         // 外键：删帖清孤儿、按帖查询
  parentId: '',           // 挂在谁下面（一级为空）
  depth: 0,               // 0 一级 / 1 二级，三级折回二级
  replyToOpenid: '',      // 「回复 @某某」是谁（与 parentId 分开存）
  replyToAuthor: '',
  author: '浙小商', avatarUrl: '', authorOpenid: 'o...',
  content: '', images: [],
  likes: 0, dislikes: 0,
  removed: false,         // 软删标记，读的一侧按它过滤
  removedAt: 0, removedBy: '', removedReason: '', appealable: false,
  time: '2026-10-17', at: 1759...
}
```

老数据不用手工搬：`migrateLegacyComments` 在「有人打开这条帖子 / 发留言 / 点赞 / 举报」
时惰性迁移一次，靠 `posts.commentsMigrated` 的条件更新抢锁，**全部写成功才清掉原数组**
（原数组是唯一副本，中途失败就留着下次重试）。迁移完 `posts.comments` 字段被删除，
只留 `commentCount`。

### 1.2 `chats.rev` 是干什么的

`chats.messages` 是一个数组。发消息走原子 `push`，但「改其中一条」（撤回、摘掉
违规图）没法只改一条，只能把整个数组读出来、改一处、再整份写回去 —— 而这一次
写回会把这段时间里 `push` 进来的新消息一起抹掉。表现是「刚发出去的话，一刷新
就没了」，只在两人同时说话时偶发，查日志什么都看不出来。

所以会话上多了一个计数器：

| 字段 | 谁写 | 含义 |
|---|---|---|
| `rev` | `chatSend` / 解除好友的系统消息：`db.command.inc(1)`；新建会话：`1` | `messages` 被写过几次 |

`chatUpdateMessages(chatId, mutate)` 是唯一的整份写回入口，做法是读 → 改 →
`where({_id, rev}).update({..., rev: rev + 1})`。命中 0 条说明读完之后有人
`push` 过（`rev` 已经变了），重读重算，最多 3 次，还不行就回 `busy` 让用户重试。

老会话没有这个字段：第一次走 CAS 时会先用 `db.command.inc(0)` 补一个 0
（字段不存在时结果是 0，已存在时原地不动，不会抹掉并发那次 `+1`），再进 CAS。

> 新增任何「改 `chats.messages` 里某一条」的功能，都必须走 `chatUpdateMessages`，
> 不要再写 `.update({ data: { messages: 变量 } })`。`test-fix-20261017.cjs` ⑪
> 有一条守卫会扫出来。

## 2. 权限怎么设

> **先说清楚名字对不上这件事**：这一节以前写的「仅管理端可读写」**不是控制台里的原话**，
> 控制台（数据库 → 数据权限）实际只有五项，选的时候别选错：
>
> | 控制台里的原文 | 本文件的说法 | 谁能读写 |
> |---|---|---|
> | 所有用户可读，仅创建者可读写 | 所有用户可读，仅创建者可写 | 前端可读全部；不能写 |
> | 仅创建者可读写 | ——（本项目不用） | 前端只能读写 `_openid` 是自己的记录 |
> | 所有用户可读 | ——（本项目不用） | 前端可读全部，谁都不能写 |
> | **所有用户不可读写** | **仅管理端可读写** | 前端完全访问不到，只有云函数、控制台能动 |
> | 自定义安全规则 | ——（本项目不用） | 自己写 JSON |
>
> ⚠️ **「仅创建者可读写」不等于「仅管理端」**，两者不能混。它按**记录**判权限：
> 云函数写进去的文档没有 `_openid`，所以看起来也读不到 —— 但那是巧合。
> 只要哪条记录带了 `_openid`（比如有人从小程序端写过一次），那条就对前端公开了。
> 私有集合一律选**「所有用户不可读写」**，语义才是确定的。
>
> 注意界面顶部那句提示：**云控制台和服务端始终拥有全部读写权限**，
> 这些配置**只约束小程序端发起的请求**。云函数怎么查都不受影响。

默认推荐：

| 权限（控制台选项） | 适用集合 | 理由 |
|---|---|---|
| **所有用户可读** | `posts` `reviews` `courses` | 只有这三个是**前端直连读**的（`utils/store-sync.js` 的 `fetchAll()` 按页直接 `db.collection().get()`）。该档只读，写全部走云函数；绝不能选「所有用户可读，仅创建者可读写」，否则创作者可绕过云函数直接写库。 |
| **所有用户不可读写** | 其余 34 个（含 `comment_votes` `post_comments` `comment_appeals` `content_protects` `content_views`） | 读写全部经过 `user` 云函数；`content_views` 尤其不能让客户端直连 —— 谁写得分母，谁就能让自己的帖子永远达不到下架线 |

> **`content_views` 为什么连「只读」都不能放开**（常被问：放开只读不就能让大家看到浏览量了？）
>
> 不能，而且没必要。两件事分开看：
>
> 1. **看不到数字，跟权限无关。** 浏览量是 `contentView` 云函数的返回值，
>    `contentView` 在云函数内部 `count()` 完把数字回给前端。集合权限管的是
>    「客户端能不能直接 `db.collection(...).get()`」，跟这个数字怎么显示毫无关系。
>    想让人看到浏览量，缺的是**页面上的那一行字**，不是集合权限。
> 2. **放开的代价是公开阅读记录。** 这个集合一行记一个浏览者，字段里有明文 `openid`，
>    `_id` 也拼着 openid（`post_<内容id>_<openid>`）。云开发的权限是**文档级**，
>    没法「只公开计数、不公开 openid」。一旦设成所有用户可读，任何人都能拉出
>    「谁看过哪条内容」的完整清单 —— 它比 `comment_votes` 更敏感：
>    点赞好歹是一次表态，浏览是没打算留痕的行为。
>
> 想让浏览数出现在更多地方（列表页），正确做法是让**云函数**在列表接口里带出来，
> 而不是把这张表开放出去。目前它在帖子 / 闲置 / 活动的详情页显示，
> 且**达到 50 人才出现**（`utils/config.js` 的 `VIEW_SHOW_MIN`）——
> 低数字会让新用户以为「这个平台没人」，理由见 `docs/report-thresholds.md`。

关键的一点，想清楚就不会设错：

> **云函数里访问数据库走的是"管理端"身份，不受"仅创建者可读写 / 所有用户不可读写"的限制。**
> 所以这两档权限对云函数来说都一样能用，区别**只在于客户端能不能直接读**。
>
> 换句话说：把 `notifications` / `blocks` / `contacts` / `chats` 设成"所有用户可读"，
> 等于把全校同学的好友申请、拉黑名单和私信内容公开出去。这几个集合的读取**全走云函数**，
> 云函数会按 openid 过滤 —— 客户端没有任何理由直接读它们。

⚠️ **写入一律不给客户端。** 前端不直连写任何集合（可以 `grep -rn "cloud.db()" utils pages`
确认，只出现在 `store-sync.js` 与 `store-forum.js` 的读取里）。点赞早就在服务端收口了
（记在帖子的 `likedBy` 数组里），让客户端能写 `likes` 等于能无限刷赞。

## 3. 索引清单

> 这一节是**扫代码扫出来的**（遍历 `cloudfunctions/user/index.js` 里每一个
> `.orderBy()`，回溯它前面配了哪些 `.where()`），不是凭记忆写的。
> 云函数改了查询，请回来同步这一节。
>
> **一共只有 7 个是"不建就报错"的**，列在 3.1。其余都是"不建也能跑，只是慢"。

### 3.1 必须建（缺了查询**直接报错**）

云开发的 `where(...) + orderBy(...)` 走的是**复合索引**。没建索引时查询会失败，
而调用点外面普遍套着 `.catch(() => ({ data: [] }))` —— 于是错误被吞掉，
界面上看到的是"空列表"，用户当成"真的没有"，日志里什么都查不到。
**「好友申请收不到」这个 bug 的根因就是它**（见 `listRequests` 上方那段注释）。

云开发控制台 → 数据库 → 选中集合 → **「索引管理」页签** → 「添加索引」。每一项要填的：

| 表单里的项 | 怎么填 |
|---|---|
| 索引名称 | 自己起，能看出用途就行，如 `idx_openid_at`。只影响控制台显示，代码里用不到 |
| **唯一** | 一律选**「否」**。选了「是」，只要库里出现两条该字段组合相同的记录，写入会直接失败 —— 而这些集合里几乎没有哪对字段天然唯一 |
| 字段 | 按下表顺序**逐个添加**，每个字段单独选升序 / 降序 |
| 排序方向 | 表里写「升序 + 降序」就不能两个都升序。复合索引是**有方向**的，`at 降序` 和 `at 升序` 是两个不同的索引 |
| 生效 | 点确定后**立即生效**，不用重新部署云函数，不用重建集合 |

> 复合索引只能按**前缀**匹配：`openid + at` 能服务 `where(openid).orderBy(at)`，也能服务只查 `openid` 的；
> 但反过来建 `at + openid` 就一条都用不上。所以字段顺序照抄下表，别自己调。

| # | 集合 | 索引字段 | 谁在用 | 缺了会怎样 |
|---|---|---|---|---|
| 1 | `chats` | `a` 升序 + `updatedAt` 降序 | `chatList` 的 or 左半支 | 私信主列表 + 消息请求箱全空，页面提示"暂时读不到会话" |
| 2 | `chats` | `b` 升序 + `updatedAt` 降序 | `chatList` 的 or 右半支 | 同上。`or` 会被拆成两个分支，**每个分支各要一个索引**，只建一个不够 |
| 3 | `posts` | `authorOpenid` 升序 + `at` 降序 | `postsByAuthor` | 名片页「TA 的历史发帖」永远空 |
| 4 | `posts` | `openid` 升序 + `at` 降序 | `postsByAuthor`（老帖那一路） | 同上，早期从云端同步上来的老帖查不出来 |
| 5 | `reports` | `status` 升序 + `at` 降序 | `getQueue` | 审核页「待处理」永远空 |
| 6 | `memos` | `openid` 升序 + `at` 降序 | `memoList` | 备忘录读不出来 |
| 7 | `market` | `type` 升序 + `at` 降序 | `marketList` 带分类时 | 切「失物 / 二手」分类后列表空 |
| 8 | `posts` | `pinned` 升序 + `pinUntil` 升序 | `pinSweep`（定时收回到期置顶） | 到期的置顶永远留在库里：读的一侧仍会隐藏，但管理页的「置顶 (N)」和 10 条名额会一直被占着，表现为「明明没置顶了却说满了」 |

> 3 / 4 是一条语句里的两个分支（`Promise.all` 各查一次再合并），
> 不是两个不同页面的需求 —— 建的时候别漏掉第 4 条，它负责的正是最老的那批帖。
>
> 建完之后这几处**如果还是空的**，那就真的是没有数据，不是索引问题。

### 3.2 建议建（不建也能查，但每次全表扫 + Console 刷"建议索引"告警）

这些是**只有 `orderBy`、没有 `where`** 的查询：

| 集合 | 索引字段 | 谁在用 |
|---|---|---|
| `posts` | `time` 降序 | **前端直连**：`utils/store-sync.js` 启动分页拉列表（前端读 `posts` 是唯一被放行的直连读） |
| `market` | `at` 降序 | `marketList` 不带分类时（与上一条互斥，两个都建） |
| `events` | `at` 降序 | `eventList` |
| `resources` | `at` 降序 | `resourceList`（公开列表） |
| `resources` | `status` 升序 + `at` 降序 | `resourceQueue`（审核员待审队列；新上传资料是 `pending`） |
| `places` | `at` 降序 | `placeList` |
| `mod_logs` | `at` 降序 | `modLogs`（审核日志按时间倒序） |
| `content_protects` | `at` 降序 | `protectList`（已保护清单按时间倒序） |
| `calendar` | `date` 升序 | `calendarList`（校历按日期**正序**，不是倒序） |

### 3.3 量涨起来再说（纯 `where`，无 `orderBy`）

这类当前**不会报错**，只是全表扫。数据量还在几百条时无感，先不建也行。
代码里一共有 40 多处这类查询，这里只列最常用的：

| 集合 | 索引字段 | 谁在用 |
|---|---|---|
| `contacts` | `toOpenid` + `status` | `listRequests`（别人发给我的申请） |
| `contacts` | `fromOpenid` + `status` | `listOutgoing` / `listFriends` |
| `notifications` | `openid` | `notifyList` |
| `notifications` | `openid` + `read` | 未读计数 / 全部已读 |
| `chats` | `key` | `chatSend` / `chatRead` 每次按会话 key 取 |
| `media_audit` | `traceId` | 审核回执对账 |
| `media_audit` | `status` | 定时兜底扫 `pending` |
| `friends` | `openid` | `friendIdSet` / 备注名 |
| `users` | `banned` | `banList`（审核页「封禁名册」每次进页扫一遍） |
| `blocks` | `openid` | 拉黑名单 |
| `event_joins` | `eventId` / `openid` | 报名名单 / 我报名的 |
| `post_votes` | `postId` + `kind` | 投票结果 |
| `comment_votes` | `commentId` + `kind` | 留言赞踩数人头（`commentVote` 每次点赞都数两遍） |
| `comment_votes` | `postId` | 删帖时顺手清掉这条帖的投票记录 |
| `post_comments` | `postId` | **评论区主查询**：`listCommentsOfPost` 每页 100 条翻页；删帖清孤儿、软删子树也按它扫 |
| `post_comments` | `postId` + `authorOpenid` | `postComment` 的三道闸（判重 / 判频率）每次发留言都查一遍 |
| `comment_appeals` | `status` | `appealQueue` 审核页每次进页扫 `pending` |
| `reports` | `status` + `targetType` + `targetId` | 管理员直删后归档该内容的待处理举报（`archivePendingReportsForDeleted`） |
| `reports` | `status` + `targetType` + `postId` | 删帖时连带归档该帖下所有留言举报 |
| `content_views` | `targetType` + `targetId` | **每次打开详情页都要数一遍**（`contentView` 回浏览人数）、每次举报也要数（`countViews` 算门槛分母）。不建索引会随浏览记录增长越来越慢 |

| `bottle_logs` | `key` | 捞瓶次数（每天 3 次） |

> ⚠️ 上表里 **`content_views` 例外，建议现在就建**，别等「量涨起来」：
> 它每打开一次详情页就 `count()` 一次（`contentView` 要把人数回给页面），
> 每次举报还要再 `count()` 一次（算下架门槛的分母），是这批里唯一的高频查询。
> 记录涨到几万条还没索引时，表现是**详情页越用越慢**，而不会报任何错。
>
> 建法只有一条：字段 `targetType` 升序 + `targetId` 升序，**唯一性选「否」**。
> 不要给 `openid` 建索引 —— 查询里它是 `neq`（排除作者），用不上索引前缀，
> 建了只是白白增加写入开销。一人只算一次的保证来自 `_id`，不靠索引。

### 3.4 不用建

| 集合 / 索引 | 为什么 |
|---|---|
| `account_reqs` | 定时器 `.limit(20).get()` 全量扫，待注销人数是个位数 |
| `errors` | 只写不查（没有读取 action）。要看出去云开发控制台 → 数据库 → `errors`，按 `at` 倒序看 |
| `favorites` | `_id = openid`，按 doc 直取 |
| `app_config` | `doc('submsg')` 直取 |
| `reviews` / `courses` | 前端直连是 `.limit(500).get()` 全量拉，**既没有 where 也没有 orderBy**，不需要索引 |
| **`posts` 的 `at` 单字段降序** | ⚠️ 历史条目，**当前代码用不到**。前端分页只按 `time` 倒序（见 3.2），云函数里 `at` 一律是跟 `where` 配对出现的（已进 3.1）。现在没有任何"裸 `orderBy('at')`"的查询。哪天把排序字段改成 `at` 了再建 |

### 3.5 怎么知道哪些还没建

**集合**不用猜：小程序里进「我的 → 环境自检」（云函数 `diag` action），
页面会直接列出 `missing`，就是还没建的集合。

**索引**没有这种一键自查，但有三个办法：

1. 控制台逐个点：数据库 → 选中集合 → 索引管理，已建的都列着
2. 看控制台的**系统推荐索引**（它按实际查询给建议，但只有查过才会出现）
3. **症状反查** —— 这条最快：

| 你看到的现象 | 缺的索引 |
|---|---|
| 私信列表 / 消息请求箱空，提示"暂时读不到会话" | `chats` 的 `a`、`b` 两个（3.1 之 1、2） |
| 名片页「TA 的历史发帖」空 | `posts` 的 `authorOpenid`、`openid`（3.1 之 3、4） |
| 审核页「待处理」空 | `reports` 的 `status`（3.1 之 5） |
| 备忘录打不开 | `memos` 的 `openid`（3.1 之 6） |
| 市场切分类后列表空 | `market` 的 `type`（3.1 之 7） |

⚠️ 最后一列：这五类问题的共同点是**没有任何前台报错**。
用户看到的永远是"这里没东西"，而不是"出错了"。

## 4. 图片审核回调（消息推送）怎么配

### 4.1 为什么必须配

图片走的是微信官方**异步**审核（`security.mediaCheckAsync`）：提交时只拿回一个 `traceId`，
结论由微信侧处理完后**主动推**给小程序。没配的话结论永远回不来，
10 分钟后被兜底扫描标成 `unverified` 并放行 —— **功能不断，但审核形同虚设**。

### 4.2 入口在云开发控制台，不在公众平台

⚠️ 这是最容易走错的一步，本项目之前的文档也写错过：

| 入口 | 用途 | 要不要走 |
|---|---|---|
| `mp.weixin.qq.com` → 开发 → 开发管理 → 开发设置 → **消息推送** | 给**自建服务器**用的（要填 URL + Token + EncodingAESKey） | 我们没有服务器，**不走这条** |
| 云开发控制台 → 设置 → 其他设置 → **消息推送** | 给**云函数**用的 | ✅ 走这条 |

两者是互斥的：官方文档原话 —— 「如在云函数中配置了某个类型的消息，
该类型消息将**不再推送**至『微信公众平台 - 开发设置 - 消息推送』中配置的域名」。
也就是说在公众平台那边费劲配完，云开发这边一开就把它废了。

两个都能进（选一个即可）：

- 微信开发者工具 → 顶部「云开发」→ 设置 → 其他设置 → 消息推送
- 或 <https://tcb.cloud.tencent.com> → 选环境 → 环境设置 → 消息推送

### 4.3 四步配完

1. **推送模式**选「**云函数**」（不是 URL）
2. 点「**添加消息推送**」，三个字段这样填：

   | 字段 | 填什么 | 为什么 |
   |---|---|---|
   | 消息类型 | `event` | 对应收包的 `MsgType`。`wxa_media_check` 是**事件**不是文本消息，所以不能填 `text` |
   | 事件类型 | `wxa_media_check` | 对应收包的 `Event` |
   | 云函数 | `user` | 回执落在 `cloudfunctions/user/index.js` |

3. 保存
4. 确认 `user` 云函数**已经部署过**——没部署的话下拉里根本选不到它。
   部署：开发者工具里右键 `cloudfunctions/user` → 上传并部署（云端安装依赖）

> 同一个「消息类型 + 事件类型」二元组只能推到一个环境的一个云函数，
> 配重了会互相抢，后配的生效。本项目只有这一条，不冲突。

### 4.4 前置条件：openapi 权限

`cloudfunctions/user/config.json` 里必须声明，否则 `cloud.openapi.security.mediaCheckAsync`
是 `undefined`，代码会直接 `return` 放行 —— **图片一张都不进审核，且不报任何错**。

```json
{
  "permissions": {
    "openapi": [
      "security.msgSecCheck",
      "security.mediaCheckAsync",
      "subscribeMessage.send"
    ]
  }
}
```

本项目已经写好了。**「发了带图的帖子但一条审核记录都没有」时，先查这里。**

### 4.5 验收

1. 真机（或开发者工具）发一条**带图**的帖子
2. 云开发控制台 → 数据库 → `media_audit` 集合 → 刷新
3. 官方说 30 分钟内推到，实测一张图 5~10 秒就到

| 你看到的 | 结论 |
|---|---|
| 有记录，几秒内 `pending` → `pass` / `risky` | ✅ 通了 |
| 有记录，10 分钟后变 `unverified` | 提交环节通了、**推送没配通**（兜底扫兜住的） |
| `media_audit` 里**根本没有新记录** | 提交环节就没进：查 4.4 的 openapi 权限，或图片不是 `cloud://` fileID |
| 记录都在，但 `errors` 里出现 `scope=mediaOrphan` | 推送到了，但 `traceId` 对不上——多半是**另一个小程序 / 另一个环境**推过来的 |

### 4.6 三个常见坑

- **环境选错**：云开发控制台里默认是当前环境，多环境时一定要确认是
  `cloud1-your-env-id`（见 `utils/config.js` 的 `CLOUD_ENV`，提交与接收必须同一环境）
- **改了 config.json 没重新部署**：权限是随代码上传的，改完必须再部署一次
- **回执进了但没生效**：`exports.main` 里对 `wxa_media_check` 的判定必须在最前面 ——
  这类事件**没有 `action` 也没有 `openid`**，落到下面的统一校验只会得到一句
  「无法识别用户身份」。本项目已经放在顶部，新增其他推送类型时也要照此办理

### 4.7 回执到了之后会发生什么

`media_audit` 里 `status` 变成 `risky` 时，云函数会**只摘那张图、不删整条内容**
（一句话配一张违规图，文字部分未必有问题，整条删掉会把正常上下文一起弄没，
审核员事后也看不到原始现场），并给发布者记一段观察期。
